# 并发与冲突处理

> 多用户实时编辑同一项目时的并发保护模型：**Schema 时间戳冲突检测 + proper-lockfile 原子写入 + 译文乐观覆盖**，无键级锁定。

> [!warning] ⚠️ 文档矛盾（C1 枢纽页）
> `[[raw/CODEMAPS/architecture.md|architecture]]`、`[[raw/CODEMAPS/backend.md|backend]]`、`[[raw/CODEMAPS/data.md|data]]`、`[[raw/CODEMAPS/frontend.md|frontend]]`、`[[raw/CONTRIBUTING.md|CONTRIBUTING]]`、`[[raw/RUNBOOK.md|RUNBOOK]]` 均描述**键级锁定**（`lock`/`unlock` 事件、`LOCK_TIMEOUT` 30s、`LockIndicator`、`collaborationStore.locks`、按 IP 区分操作者）。
> **权威状态**：父仓库 `CLAUDE.md` —— 键级锁定已于 **2026-08-09 移除**（客户端从未接线的死代码）。当前并发保护 = **Schema 时间戳冲突检测**（`schema:rejected`）+ 数据层 **proper-lockfile 原子写入**。本项目**不做任何身份识别**（既不用 IP 也不用 cookie/session）。

## 当前并发模型

1. **Schema 变更 → 时间戳冲突检测**：客户端发送 `schema:updated` 携带 `timestamp`，服务端比对拒绝过期变更（`schema:rejected`），客户端收到后自动同步到最新已接受数据。
2. **译文变更 → last-write-wins**：后保存的覆盖先保存的（乐观覆盖），不做拒绝。
3. **文件写入 → 原子写**：`data-layer/io.ts` 的 `atomicWriteJson` 用 `proper-lockfile` 锁定目标文件（重试 5 次，50–200ms 间隔），写 `.tmp` 后 `fs.move` 替换。

## 时间戳机制细节

- 服务端维护模块级 `globalSchemaTimestamps: Map<string, number>` + `globalAcceptedData: Map<string, any>`（按 `projectId` 索引）。
- 客户端 `useSocket.nextTimestamp()` = `max(Date.now(), lastAccepted + 1)` 实现**单调校准**：收到 `schema:rejected` 时记录服务端已接受的时间戳，时钟落后的机器首次被拒后立即追平，不会被永久拒绝。
- HTTP PATCH `/schema/keys` 同样支持可选 `timestamp` 冲突检测（`schema.ts` 模块级 `lastSchemaTimestamps`），过期返回 409。
- **关键约定**：`schema:updated` 与 `schema:save` 共用同一套检测——避免"广播被拒但仍写盘"导致磁盘与所有客户端显示不一致。

## 原子写入

- `atomicWriteJson(path, data)`：`proper-lockfile` 加锁（目标文件不存在时先建空 JSON）→ 写 `.tmp` → `fs.move` 覆盖 → 释放锁。
- 这是并发安全的主要保障（断电/多进程/多请求）。

## 在线人数语义

- 按 Socket.IO 房间 `io.sockets.adapter.rooms.get(roomName).size` 统计 **socket 连接数**。
- 同浏览器开多个 tab 各计一次——统计的是**连接数而非人数**。

## 其他预留/死代码

- `overwritten` 事件：客户端有监听、服务端暂无发送点（预留）。
- `update` 通用事件：`sendUpdate` 从未被 `page.tsx` 取用，是**死代码**（见 [[architecture/Socket.IO-协议|Socket.IO 协议]]）。
